1. Executive Product Goal
Build a polished, realistic beauty e-commerce demo for the fictional brand Lumiere that demonstrates GetMyShade as a B2B shade-matching infrastructure/API.
The demo has two connected interfaces:1. Lumiere Shopper Storefront — the customer-facing shopping experience.2. Lumiere × GetMyShade Brand Admin — the brand-facing management, analytics and intelligence experience.
The most important shopper behavior is:
Product → Find Your Shade → Scan → Multiple Ranked Shade Recommendations → Match Score/Confidence → Add to Cart
GetMyShade should not force shoppers to create a GetMyShade account. The shopper can receive recommendations anonymously and take a direct commerce action.
IMPORTANT UPDATE:GetMyShade returns MULTIPLE possible recommendations, not only one shade. Each recommendation has a match score/accuracy-style level. The highest-ranked match should be visually emphasized, but every recommended shade must have its own Add to Cart action.
2. Core Product Positioning
GetMyShade is an infrastructure layer for beauty brands.
The brand owns:• Shopper relationship• Website• Product catalog• Shade catalog• Checkout• Brand experience
GetMyShade provides:• Shade analysis• Matching• Ranked recommendations• Match scores• Feedback collection• Match analytics• Integration infrastructure• Match intelligence/data layer
The shopper should feel like they are using Lumiere's website with GetMyShade seamlessly embedded into it.
3. High-Level Architecture
Lumiere Shopper Website        ↓GetMyShade Widget / SDK / API Client        ↓GetMyShade API        ↓Matching Engine        ↓Lumiere Product + Shade Catalog        ↓Ranked Match Recommendations        ↓Shopper selects a recommendation        ↓ADD TO CART        ↓Lumiere Commerce System
Separately:
GetMyShade Event/Data Layer        ↓Lumiere Brand Dashboard        ↓Analytics / Match Performance / Feedback / Commerce / Match Intelligence
Build the UI and backend with a clean abstraction layer so the current simulated/mathematical matching system can later be upgraded without rebuilding the interfaces.

17. Match Score / Accuracy Language
Use “Match” or “Match Score” as the default consumer-facing terminology.
Preferred:96% Match
Avoid claiming:96% Accuracy
unless the underlying methodology has actually validated that percentage as accuracy.
The percentage should be understood as a match/confidence-style indicator, not a guarantee.
Admin/internal systems may store a separate numerical confidence value between 0 and 1 if appropriate.

20. Direct Add-to-Cart Behavior
The primary shopper action after recommendations is ADD TO CART.
When shopper clicks Add to Cart on a recommendation:1. Add the exact recommended product/SKU/shade to Lumiere cart.2. Record the selected recommendation.3. Record recommendation rank.4. Record match score.5. Record the scan_id.6. Record the add_to_cart event.7. Show confirmation.8. Keep the shopper in the shopping experience unless they choose to view the bag.
Example:Shade 350 selectedRecommendation rank: 2Match score: 92%Added to cart: TRUE
Do NOT require the shopper to:• Return to the product page• Manually find the shade again• Create an account• Rescan
The Add to Cart action should be one of the shortest paths in the entire experience.

The shopper should not need an account to use the matching service.

Do not secretly treat identifiable or sensitive data as training data.

64. API Abstraction Rule
DO NOT hard-code the Lumiere frontend to a particular matching algorithm.
Use:
Lumiere Frontend↓GetMyShade SDK / API Client↓GetMyShade API↓Matching Engine
The frontend should only depend on the response contract.
This allows the current mathematical baseline / existing AI-assisted workflow to evolve into a stronger ML engine later without rebuilding the shopper UI.
